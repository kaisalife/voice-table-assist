## 1. 累计精简：把"最后一个三元组"反拼为下一轮前缀

**问题**：用户连续录入多行/多列时，累计文本会越积越长（"外径一号11.5二号22.5三号33.3..."），
NER 每次都重算整段；embedding 也要把整段编码成向量，延迟越来越糟。

**方案**：静默提交 → NER 完成 → 取抽回的**最后一个完整三元组** `(Sub,Obj,Val)` → 把它反拼回
字符串作为下一轮累计的开头，原始累计清空。

**为什么是"最后一个"**：NER 按用户录入顺序出三元组，最后一个三元组就是用户**当前行/列**的
最末一条。主体 Sub 保留 → 下一段语音省略行标签时仍能匹配；Obj+Val 是已识别完成值，不会重复回填。

**守卫**（防误精简）：
- NER 抽回 0 个三元组 → 保留原累计（主体尚未出现，重写会丢前置内容）。
- 末尾三元组含占位 `?`（OBJ/VAL 缺一）→ 保留原累计，避免拼出"硬度?/十一点五?"。
- Sub 为空 → 保留（防御 NER 偶发不抽到 SUB 但 OBJ/VAL 已识别的情况）。

**例子**：
- 累计 = `外径一号11.5二号22.5` → NER 出 2 个三元组 → 末三元组 = `(外径,二号,22.5)`。
- 下一轮累计 = `外径二号22.5`（原始清空）。
- 用户继续"三号33.3" → `MergeText` 接上去 → `外径二号22.5 三号33.3` → NER 再抽 2 个三元组。

**收益**：NER/embedding 重算字符数从整段 → 1 条三元组；前端不再收到前几条 cells 的重复回放。

代码：`Asr/VoiceInteractionSession.cs:SubmitAsync`，commit `9747670`。

## 2. 单连接门卫："新连接接管旧连接"取代 409 拒接

**问题**：单用户/单平板场景里，"按一次按钮发起新连接"**就是**旧连接过时的信号；
旧实现是握手时回 HTTP 409 拒接，导致用户需要先关闭旧页面才能开新页。

**方案**：服务端用单飞计数 + `CancellationTokenSource` 持有"当前会话位"：
- 新连接进入时，**先取消旧会话的 token**（旧连接的 `ReceiveAsync` 抛 OCE，finally 清理）。
- 再登记本次新会话，返回新 token。
- 旧连接断开后调用 `ReleaseSession`，但**仅当传入的 cts 仍是当前会话时才清空**（`ReferenceEquals` 保护）——被接管的旧会话释放时不会误清新会话。

**为什么这样安全**：`ReferenceEquals` 决定"被释放的 cts 是不是当前座位"——如果旧会话的 cts 还没轮到
自己释放，token 已经被 cancel 了，但此时 `_sessionCts` 已经指向新会话；旧会话的 `finally` 触发时
`ReferenceEquals(_sessionCts, oldCts) == false`，不会动新会话的座位。

**收益**：单用户场景里"按按钮就连上"是唯一合理的行为；多连接被从根上砍掉，规避切表/抢占/状态污染。

代码：`Services/EngineHost.cs:AcquireSession / ReleaseSession`，commit `55c1fea`。

## 3. 停的时候不丢 cells：partial 收尾 + 不抢先关 socket

**问题**：用户点"结束"按钮时，最近一条识别片段常常还在 sherpa 的 partial 队列里，**没进 final**。
旧实现是立刻关 socket，结果 sherpa 把 final/cells 还没回完，连接就被前端撕了——cells 永远不显示。

**方案**（两步）：

1. **partial 收尾**：前端在 stop 之前不再用"固定 800ms 抢先关 socket"。改保留 socket 等服务端
   把 final 推回来 + NER 走完 + cells 推回 + 服务端主动关连接。前端只发 `{type:'stop'}` 然后等
   `onclose`，配 8s 兜底超时。
2. **partial fold**：服务端在停路径里，把"最近一条 partial"通过 `FoldPartial(text)` 补
   fold 进累计（**不触发静默计时器、不触发超限清空**），再走 `FlushAsync` → NER → cells。
   这样即使 sherpa 来不及切 final，端点前的最后一条字也不会丢。

**为什么 fold 不触发计时器**：折叠只服务本次的"最后一下"——fold 完就立即走 FlushAsync，
如果触发计时器反而会让计时器在 partial 入累计后被白白重启，拖长 cells 下发。

代码：`Asr/SherpaAsrBridge.cs:ForwardBrowserAudioAsync`（停路径 fold）、
`Asr/VoiceInteractionSession.cs:FoldPartial`（fold 实现）、
`wwwroot/voice-mic.js:stop()`（前端不再抢先关），commit `2379ad3`。

## 4. 测试体系：纯函数 + 1 个端到端（不进部署包）

**问题**：早期没测试，OnFinal/MergeText 改一行心里没底；生产 bug 直接上线。

**方案**（分层）：

| 层 | 文件 | 用例 | 耗时 |
|---|---|---|---|
| 纯函数（毫秒级、无模型依赖） | `tests/.../Asr/MergeTextTests.cs` | 10 | < 1ms |
| 纯函数 | `tests/.../Asr/HomophoneReplacerTests.cs` | 12 | < 1ms |
| 纯函数 | `tests/.../Services/TripleExtractorTests.cs` | 11 | < 1ms |
| 纯函数 | `tests/.../Services/ChineseNumeralTests.cs` | 18 | < 1ms |
| 端到端（按行扫整表 6×4） | `tests/.../Integration/TableImportAndLookupTests.cs` | **1** | ~3s |
| **合计** | | **52** | **~3-15s** |

**不进部署包**（3 层保险）：

1. 主 csproj 显式 `<Compile Remove="tests\**" />` + `<Content Remove="tests\**" />` + `<None Remove="tests\**" />`。
2. `publish.bat` 显式只 `dotnet publish "VoiceTableAssist.csproj"`，不传 .sln（避免 SDK 把 tests 项目也纳入）。
3. `publish.bat` step 1.5 兜底：`if exist "%PUBLISH%tests"` 立刻中止并提示"测试代码被错误发布"。

`.gitignore` 也加 `tests/bin/` 和 `tests/obj/`，防止测试构建产物入库。

**端到端测什么**：`NerPlusEmbedding_EndToEnd_ByRow` 把整表 6 行 × 4 列跑一遍：
每行拼一句"行标签 + 测量值N + 中文值 + 测量值N+1 + 中文值 + ..."（"外径测量值一11.11测量值二22.22..."），
送 NER 期望抽 4 个三元组，每个三元组独立走 embedding 查 sub+obj，期望全部命中正确 (row, col)。
任何 NER 跨行/跨列错位都会立即出现在测试报告里。

**为什么不堆更多集成测试**：ONNX 加载一次 2-3 秒，加 10 个集成测试 = 30 秒拖慢 commit 流程，收益不如
纯函数大。核心链路用 1 个端到端守门，旁证用 51 个毫秒级纯函数。

## 5. GTCRN 进程内降噪：不动 sherpa 二进制的工厂抗噪

**问题**：工厂噪声（风机/空压机稳态噪声 + 冲压瞬态）会击穿 sherpa 的"2s trailing silence"端点判定，
用户说完 cells 不下发。sherpa-onnx 的 GTCRN 在线降噪 2026-03（v1.12.30, PR #3324）才进
`online-websocket-server` CLI，项目用的 2025-06-30 二进制不支持，升级二进制有回归风险。

**方案**：在 .NET 进程内直接跑 GTCRN ONNX（`gtcrn_simple.onnx`，48.2K 参数，522KB），
逐行移植 sherpa-onnx 的参考实现（`online-speech-denoiser-stft-impl.h` + `-gtcrn-impl.h`）：

- √hann 窗（模型元数据 `window_type=hann_sqrt`）+ n_fft=512 + hop=256 流式 STFT；
- 每 hop：加窗 → 前向 DFT → ONNX（mix + 3 个状态缓存）→ 逆向 DFT → 加窗 → overlap-add → 输出 hop 段；
- 3 个 GRU/卷积状态缓存跨帧携带；会话开始 `Reset()`、stop 时 flush，防跨会话串音。

**为什么不升级 sherpa 而是进程内实现**：升级要换 exe + 全套 dll + 重测端点/热词/ASR 全链路，回归面大；
进程内实现零 sherpa 改动、可配置开关回退（`AsrProvider.Denoise.Enabled=false` 即回到原路径），
且降噪与 ASR 解耦——GTCRN 只清频谱噪声，语言无关，对中文 0 影响。

**实测**：sherpa 官方带噪样例 RMS -25.7%（0.0850→0.0632）；现场实测语音识别无退化、
稳态噪声场景端点切句恢复。算法延迟 +33ms（相对 2.5s 静默阈值无感）。

代码：`Asr/GtcrnDenoiser.cs`（DSP+ONNX）、`Infrastructure/Config.cs:DenoiseOptions`、
`Asr/SherpaAsrBridge.cs`（PCM 上行接入 + 会话生命周期清态）。


虽然降噪对中文"无影响"，但有 2 个降噪本身的边角可能让你感觉到"中文识别率变差"——这不是"中文不支持"，是降噪模型的过度清理或频带丢失：

边界 1：女声/童声/远距离麦克风
现象：弱声被降噪当成"噪声"清掉
原因：GTCRN 默认训练数据以成年男声为主
影响：实际是任何弱声都受影响，不分语言
缓解：在降噪后端接 AGC（自动增益控制），把弱声拉回正常电平
边界 2：爆破音（b, p, t）和送气音（ch, q, c）
现象：清辅音听起来"模糊"
原因：GTCRN 的频谱掩码有时会压低短时高频能量
影响：中文里"四/十"、"爸/八"这种靠送气音区分的对子可能识别率下降（其实即使没降噪，sherpa 对这些对子也容易错）
缓解：在热词文件 hotwords.txt 里加送气音敏感词、加大 hotwords_score
