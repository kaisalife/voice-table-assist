# 安卓化方案（方案 A：纯 C/C++ + Android Native Service + AIDL）

> **目的**：把 `smart-inspection-voice-gateway-dotnet8`（现 .NET 8 + sherpa-onnx + 本地 ASR / NER / 嵌入 / HR / GTCRN 降噪）整套能力**塞进安卓平板，离线运行，由企业 App 通过 AIDL 调用，**不**带 UI**。
>
> **状态**：设计稿，多处标 `【待定】`——这些是必须跟企业 App 团队 / 集成方对齐后才能定的事项。

---

## 0. 范围与边界

### 0.1 要做的事

- 把现 .NET 8 网关的 **ASR + GTCRN 降噪 + RaNER + 嵌入 + 同音纠正 + 多表管理 + partial/final/cells 编排** 全部跑在平板本地。
- 暴露一套 **Android AIDL 接口**，让外部企业 App 通过 Binder 调。
- 工程实现：纯 **C/C++**，Android 端一个 **Native Service** 进程；不写 Java/Kotlin 业务代码（AIDL 自动生成的桩除外）。

### 0.2 不做的事

- **不**做 UI（前端由企业 App 负责）。
- **不**保留现网 .NET HTTP/WS 端点（除非企业 App 要求，否则平板只通过 AIDL 暴露）。
- **不**带 `sherpa-onnx-online-websocket-server.exe` 这个进程（不跨 ABI）；改用 **JNI 调 sherpa-onnx C++ 库** 起 `OnlineStream` / `OnlineRecognizer`。

### 0.3 跟现网代码的关系

- **不复用 C# 代码**：.NET 那层与 Native Service 是两个独立进程，跨进程只能 AIDL。
- **可复用模型 ONNX**：`encoder.onnx` (588MB) / `decoder.onnx` / `joiner.onnx` / `model.onnx` (RaNER) / `model_quantized.onnx` (gte-base-zh) / `gtcrn_simple.onnx` 全部直接拷贝；`tokens.txt` / 热词 / HR 规则表 / 表注册表等数据文件直接拷（路径改 Android 内部存储）。
- **算法逻辑逐句翻译**：C# 的 `SherpaAsrBridge` / `GtcrnDenoiser` / `RaNerEngine` / `EmbeddingEngine` / `TableVectorManager` / `HomophoneReplacer` / `VoiceInteractionSession` 全部重写成 C++，放同一进程（一个 Native Service）——减少 IPC。

## 3. AIDL 对外接口（草稿）

> 命名空间 `com.vta`；包名沿用 `smart-inspection-voice-gateway` 派生（占位）。所有 Java/Kotlin 代码**只由 AIDL 编译器自动生成**，不手写。

### 3.1 AIDL 主接口

```java
// aidl/com/vta/IVtaService.aidl  ——  AIDL 语法，业务侧不实现
package com.vta;

import com.vta.PcmFrame;
import com.vta.SessionState;
import com.vta.TableInfo;
import com.vta.CellHit;

interface IVtaService {

    // 生命周期
    int getVersion();
    String health();                       // 返回 "ok" / 启动中 / 错误

    // 表格管理  【待定：增删查?】
    List<TableInfo> listTables();
    TableInfo getTable(String name);
    // int importTable(String jsonOrCsv);   // 【待定】
    // int removeTable(String name);        // 【待定】

    // 热词 / 同音纠正  【待定】
    // int setHotwords(String tableName, String[] words, float score);
    // int setHrRules(String tableName, String path);

    // 语音会话：流式接口
    // captureMode: 0 = Service 自主采音（默认，推荐，见 §6.1）；1 = 企业 App pushPcm 喂流
    int openSession(String tableName, int silenceMs, int captureMode);  // 返回 sessionId；409 = 已有
    int pushPcm(int sessionId, in PcmFrame frame);      // captureMode=1 时喂 float32 PCM（每块 10~100ms）
    SessionState getState(int sessionId);
    CellHit[] pollCells(int sessionId, int maxN);       // 阻塞拉取累积的 cells
    int closeSession(int sessionId);
}
```

回调用 **轮询 `pollCells`**，避免 AIDL 跨进程回调的复杂时序——更稳、调试容易。

### 3.2 Parcelable

```java
// PcmFrame.aidl —— 16kHz float32 单声道 PCM 块
package com.vta;
parcelable PcmFrame {
    long timestampMs;       // 企业 App 自己写，服务端不解析
    float[] samples;        // 10~100ms 长度（160~1600 样本）
}

// SessionState.aidl
package com.vta;
parcelable SessionState {
    int sessionId;
    String tableName;
    String phase;           // "idle" / "listening" / "endpointing" / "closed"
    String partial;         // 当前 partial 文本
    long lastPartialMs;
}

// TableInfo.aidl
package com.vta;
parcelable TableInfo {
    String name;            // 表名（如"锅炉巡检"）
    String key;             // 安全 key（SanitizeTableKey）
    int rows;
    int columns;
    long updatedAtMs;
}

// CellHit.aidl —— 一次「说完了」的解析结果
package com.vta;
parcelable CellHit {
    int row;                // 0-indexed
    int column;             // 0-indexed
    String value;           // 归一后的字符串，如 "17.84"
    String raw;             // 原始 ASR 文本片段（"十七点八四"）
    long finalizedAtMs;
}
```

### 3.3 "单连接门卫" 在本地版的语义变化

现网是"全机一路语音连接"（`SherpaAsrBridge` 用 token 实现）。Native Service 改成 **per-app 一路**：

- 每个企业 App 连进来时给一个 `clientId`（在 AIDL bind 时拿）；
- `openSession` 时按 `clientId` 检查是否已有 session，**已有则 409**；
- 不同 App 可同时各开一路（每路消耗 ~1.2GB RAM + ASR 推理 CPU；普通平板撑不住"多路"，**【待定：限制 1 路，还是 N 路】**）。

### 3.4 partial/final/cells 三类事件

Native Service **不主动 push**。轮询模式：

- 企业 App 起线程，每 50~100ms 调一次 `getState(sessionId)` 拿 partial 文本做"识别中"提示；
- 端点触发后（Service 内部 `SilenceMs` 计时），完成 RaNER + 向量库命中，调 `pollCells` 拿到新 cells。
- 客户端拿到 `CellHit[]` 即完成一次"录入"。

## 5. 关键设计点

### 5.1 sherpa-onnx C++ 集成

- 编译：`sherpa-onnx` master（≥ 2025-12）已有官方 `aar` 和 cmake 集成。
- 加载：`dlopen("libsherpa-onnx.so")` + 调 `OnlineRecognizer`。
- 在线流：`OnlineStream` 接受 `AcceptWaveform(expected_sample_rate=16000, ...)`；循环 `IsEndpoint()` / `GetResult()` 拿 partial。
- 端点：`EndpointConfig.rule1.min_trailing_silence = 2.5`，与现网一致。
- HR：构造 `HomophoneReplacerConfig` 注入 lexicon / rule_fsts / rule_fars / hotwords_file；启动时一次性从 `assets/models/sherpa-onnx/hr/tables/<key>/` 加载。

### 5.2 GTCRN 降噪

- 现 `Asr/GtcrnDenoiser.cs` 的 STFT/ISTFT/状态缓存/overlap-add 逻辑**逐句翻译**到 C++。
- ONNX 推理走 **ONNX Runtime C++ API**（onnxruntime-android aar 提供）。
- session 启动时 `Reset()`，session 关闭时 `flush`（与现 .NET 实现一致）。
- **默认关闭**（与现网 `AsrProvider.Denoise.Enabled=false` 一致，2026-09-11 决策）：工厂噪声现场按需开启。
  端侧部署多走"车间平板 + 工厂噪声"场景，预计开启率高——建议 AIDL 暴露 `setDenoise(bool)` 运行时开关，
  而非只在配置文件里写死。

### 5.3 RaNER（BERT+CRF）C++ 实现

- ONNX Runtime C++ 跑 `model.onnx`。
- CRF 解码：照抄现 C# 代码 `Services/RaNerEngine.cs` 的 Viterbi（标签集 `O/B-SUB/I-SUB/B-OBJ/I-OBJ/B-VAL/I-VAL`）。
- `crf_transitions.json` 启动时一次性加载。

### 5.4 向量库 VTX1

- 二进制 VTX1 格式：768 维 float32，原子写（写 tmp → `rename()`）。直接用现 C# 写的格式，C++ 这边写一对一的 `vtx1_read / vtx1_write` 函数即可。
- 检索：内积（与现 `VectorIndex.cs` 一致）。表多到上万行时再上 HNSW；当前规模 6×6~10×20 暴力扫描够用。

### 5.5 HR 同音纠正 + 拼音表

- `相关文档/homophone/hr_char_pinyin.txt` 一行一字的拼音表。
- 现 C# `HomophoneReplacer.cs` 的 fuzzy match 逻辑（拼音近似 + 字符集过滤）逐句翻译。
- 数据小，启动时一次全载入内存。

### 5.6 session 编排

照搬现 `Asr/VoiceInteractionSession.cs`：
- 喂 PCM → 降噪 → sherpa partial/final → 同音纠正 → RaNER → 短语拼接 → 向量库检索 → 得 `CellHit`。
- 累计上限 `MaxChars=500`（同样可调）。
- 端点切句 2.5s（可调）。
- 切表：先 `closeSession` 再 `openSession(新表)`；与现网同约束。

### 5.7 内存与冷启动

- 冷启动：模型加载 ~8-10s（与现 .NET 网关首次 ASR 冷启动对齐）；可做"懒加载"——仅在 `openSession` 第一次被调时加载，给个 startup 进度 callback。
- 内存预算：8 GB 平板可以**同时**只跑一路（1.2-1.5 GB 工作集）；12-16 GB 平板可以**多路**（【待定：具体上限】）。
- 进程被系统杀：**offline 模式，进程死掉就完蛋**——不重连、不重试。Native Service 应注册 `START_STICKY` 让系统尽量复活。

## 6. 安全与权限（含采集架构）

### 6.1 采集架构：Service 自主采音（推荐），pushPcm 保留为兼容通道

与[语音输入权限插件版解决方案](语音输入权限插件版解决方案)探讨的结论一致：**权限问题在原生层解决最干净**。
本地版 Native Service 顺势**自带采音能力**：

```
[企业 App H5] ──(JS 桥: start/stop，不碰 getUserMedia)──►
[Native Service]
    ├─ AudioRecord 采音（VOICE_RECOGNITION 音源 / 16kHz / mono / PCM_16BIT）
    │   └─ App 级 RECORD_AUDIO 运行时权限（Service 声明并申请，无安全上下文概念）
    ├─ int16 → float32（对齐网关上行协议）
    └─ → GTCRN 降噪 → sherpa → ...（本进程内直连，零 IPC）
```

**为什么 Service 自己采音优于"企业 App 采音 + AIDL pushPcm"**：

| 维度 | Service 自主采音（推荐） | 企业 App 采音 + pushPcm |
|---|---|---|
| 权限 | Service 自己申请 RECORD_AUDIO，一次搞定 | 企业 App 也要申请 + 桥接，两套权限面 |
| 性能 | PCM 进程内直连，零拷贝零 IPC | 每块 PCM 过一次 Binder 事务（4096 样本/256ms 上限），高频开销 |
| 音源控制 | `VOICE_RECOGNITION` 固定（关系统 AGC/降噪，保留原始频谱，配合 GTCRN） | 依赖企业 App 采音参数是否正确 |
| 兼容蓝牙/USB 麦 | 系统音频路由自动生效 | 同 |

**`pushPcm` 保留为兼容通道**（AIDL 接口不变）：用于文件回放、远端 PCM 推流、企业 App 自行采集等
Service 不适合直接开麦的场景。两条通道互斥（同一 session 只能选其一）。

### 6.2 AIDL 接口增补

`openSession` 增加采集模式参数（对应 §3.1 草稿的修订）：

```java
// mode: 0 = Service 自主采音（默认，推荐）；1 = 企业 App pushPcm 喂流
int openSession(String tableName, int silenceMs, int captureMode);
```

### 6.3 其余权限项

- `RECORD_AUDIO` / `MODIFY_AUDIO_SETTINGS`：**Native Service 声明并申请**（captureMode=0 时）；
  captureMode=1 时由企业 App 自持。
- 文件存储：模型 / HR 表 / 表注册表全部放 app 私有目录 `getFilesDir()/vta/`，**不**放 sdcard（避免被其它 App 读）。
- 进程可见性：`<service android:exported="true">`（企业 App 跨进程调必须 true），但用自定义 permission
  `<permission android:name="com.vta.permission.BIND" android:protectionLevel="signature">` 锁调用方——
  **只有同一签名签名的 App 才能 bind**，避免任意 App 调用。

## 8. 验证 / 验收

### 8.1 与现 .NET 网关对齐

- 同一段 PCM（用现 `selftest/denoise-test/inp_16k.wav` 或自录）→ .NET 网关 vs Native Service 输出比对 partial / cells。
- 同音纠正规则、HR 拼音表、RaNER 标签集 — **字级别一致**。
- VTX1 向量库：**二进制格式一致**——C++ 写的 .bin C# 能读、C# 写的 .bin C++ 能读（这点要专门写一个 round-trip 单测）。

### 8.2 离线稳定性

- 拔 WiFi、拔 SIM，连续 30 分钟语音 → cells 全部到位。
- 后台锁屏 10 分钟 → service 还在（不要求像前台那样 100% 活，能被系统杀时清理 + 重启即可）。
- 冷启动 ≤ 10s（模型已在 APK 内的前提下）。
- **首次启动数值自检**：跑 sherpa 官方 test_wavs 对比输出——防 ORT 版本/SoC 组合的"静默算错"
  （zipformer encoder 在部分新 SoC 上曾出现无报错的错误结果，见 §14.4）。自检不过则拒绝进入 listening 状态并明确报错。

### 8.3 多表 / 切表

- 同一 session 切表：必须先 close。
- 多表并发：8 GB 平板一路、12 GB 平板两路（**【待定】**）。
- 切表 ≤ 1s（含 RaNER / HR 资源热加载）。

### 8.4 异常路径

- 喂空 PCM 块：service 不崩。
- 喂错采样率（44.1kHz 等）：service 拒绝并返回明确错误码（**不是 panic**）。
- binder 断开：session 自动 close，资源回收。

## 9. 风险与未决项

### 9.1 已知技术风险

| 风险 | 缓解 |
|---|---|
| sherpa-onnx C++ 升级 / ABI 变动 | 锁 v1.12.x；自建一个 fork 长期维护 |
| ONNX Runtime ARM64 推理速度 | 已实测在 Cortex-A78 上 streaming-zipformer 实时性 OK；如出现回退降级到 14M mobile 模型 |
| APK 体积超 200 MB | 拆 AAB / OBB（按表拆 asset pack） |
| 后台 Service 被杀 | `START_STICKY` + foreground service（绑一个 0 像素的常驻通知，避免被 Doze 杀）|
| AIDL 跨进程传输大块 PCM 的开销 | 限制 `pushPcm` 单块 ≤ 4096 样本（256ms）；高频小块比低频大块更省 binder 事务 |

### 9.2 未决项（**必须跟集成方对齐**）

1. **【待定】接入什么企业 App**？签名 / 包名 / 调用方式（同步 / 异步 / 推送 / 轮询）。
   > 关联：企业 App 若为 **C# + H5（MAUI）** 技术栈，其侧只需 AIDL 桥 + JS 桥两段胶水；
   > 采集走本方案 §6.1 的 Service 自主采音（H5 完全不碰 getUserMedia），与
   > [语音输入权限插件版解决方案](语音输入权限插件版解决方案) 的推荐路线同源。
2. **【待定】打包哪些表**？每张表都要在 Native Service 启动前就位，还是允许运行时 `importTable`？
3. **【待定】HR 规则 / 热词更新策略**？随 APK 升级，还是运行时热加载？
4. **【待定】多路并发上限**？8 GB 平板跑 1 路还是允许 2-3 路？
5. **【待定】是否复用现 .NET 端的部分能力**？例如：是否仍用现 .NET 网关做"远端管理后台"（HR 规则编辑、表导入、用户管理），Native Service 只跑识别？
6. **【待定】部署形态**？Native Service 单 APK 暴露 service 给任何用同签名的 App；还是把 service 内嵌到企业 App 内（同包同进程）？
7. **【待定】多语种**？当前只支持中文；如果客户有英文 / 方言需求，要不要在 Native Service 里同时跑多语种模型？
8. **【待定】GTCRN 降噪默认态**？端侧若主要落工厂噪声现场，可默认开启（现网默认关闭是"通用部署"语境）；
   若同一 APK 既要进车间又要进办公室，走 `setDenoise(bool)` 运行时开关（§5.2）。

## 10. 阶段实施建议

| 阶段 | 交付 | 依赖 |
|---|---|---|
| **P0: Hello AIDL** | 空 Native Service，AIDL `health() / getVersion()` 跑通；企业 App 能 bind，能拿到 "ok" | 1 个工程师 + AAR 集成 1-2 周（首版） |
| **P1: ASR 流式打通** | `openSession` + `pushPcm` + `getState` 跑通；partial 文本与企业 App 显示一致 | P0 + 集成 sherpa-onnx C++ 1 周 |
| **P2: 端到端 cells** | `pollCells` 出 `CellHit[]`；同一段 PCM 在 .NET 网关 vs Native Service 输出**字级一致** | P1 + RaNER + 嵌入 + HR 翻译 |
| **P3: 多表 / 切表 / 单连接门卫** | 完整业务能力 | P2 |
| **P4: GTCRN 降噪** | 工厂场景落地（如果你要复用 GTCRN） | P2 + DSP 翻译 |

每一阶段都应**保留 P0~Pn 在 .NET 网关上的对照**——别一上来全切，留回退路径。

## 13. 模型瘦身（量化 / 替代选型）

> 背景：插件/APK 形态下模型总体积 ~1.0 GB 过重。实测体积（2026-09-11）：

| 模型 | 现状 | 体积 |
|---|---|---|
| ASR encoder（streaming-zipformer-zh-2025-06-30） | fp32 | **588 MB** |
| RaNER（BERT-base + CRF） | fp32 | **388 MB**（102M 参数 × 4 字节） |
| embedding（gte-base-zh） | **已是 int8**（model_quantized.onnx） | 98 MB（无需动） |
| 其余（decoder/joiner/tokens/GTCRN/VAD/索引） | — | ~12 MB |

### 13.1 ASR 量化：官方有 int8，没有 int4

| 变体 | encoder 体积 | 状态 |
|---|---|---|
| fp32（现用） | 588 MB | 官方 release |
| fp16 | 269 MB | 官方 release |
| **int8** | **154 MB** | **官方 release 现成**：`sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30`，下载即用，热词/HR/端点全兼容 |
| int4 | — | **官方不做**。ONNX Runtime 理论上有 4-bit 权重量化（MatMulNBits），但 sherpa-onnx 的图结构+运行时未适配，实验性质，不建议赌 |

**结论**：ASR 换官方 int8 = 588→154 MB（省 434 MB），CER 代价典型 <0.5 个点，零工程量。

### 13.2 RaNER 替代：三条梯度路线（按工程量排）

**路线 ①：现有微调权重 int8 动态量化（零重训，首推）**
- BERT+CRF 动态量化是标准操作，F1 损失典型 <0.5（PaddleNLP 官方数据：ERNIE-Medium 量化后 MSRA_NER F1 93.04→92.64，只掉 0.40）
- 388 MB → **~100 MB**；已有 train.py/PyTorch checkpoint，重新导出 ONNX 时加量化即可
- 与 embedding 已走的 `model_quantized.onnx` 路径完全同构

**路线 ②：换小骨干重新微调（同款 generate_data.py 数据，代价一次训练）**

| 骨干 | 参数量 | fp32 / int8 体积 | 中文 NER 实力 |
|---|---|---|---|
| **ERNIE 3.0-Medium**（6L768H） | ~75M | ~300 / ~75 MB | MSRA_NER F1 **93.04**，官方压缩后 -0.40 |
| **RBT3**（3L768H，哈工大） | 38.5M | ~154 / ~40 MB | 小模型里均衡代表，蒸馏自 RoBERTa-wwm |
| **MiniRBT-H288**（6L288H，讯飞） | 12.3M | ~50 / **~13 MB** | 两段式蒸馏，窄而深优于 TinyBERT 同尺寸 |
| ERNIE 3.0-Nano（4L312H） | ~25M | ~100 / ~25 MB | CLUE 上 TinyBERT4 明显更强 |

- 标签体系只有 7 类 BIO（SUB/OBJ/VAL），领域数据是模板生成的（可控、量大）——**小骨干 + 自有数据**，F1 掉幅通常比公开集悲观估计小得多
- 最激进组合：MiniRBT-H288 + int8 ≈ **13 MB**，RaNER 从 388 MB 缩到 1/30

**路线 ③：UIE 范式（PaddleNLP，schema 抽取）**
- `uie-nano` 18M 参数；官方蒸馏版数据：uie-base F1 0.708 → **蒸馏 nano F1 0.767**（蒸馏版反超 base）
- 优点：schema 式提示抽取天然适配"主体/客体/数值"三元组；缺点：Paddle→ONNX 导出链路要验证，换范式 = CRF 解码逻辑重写

### 13.3 合并账本（端侧 APK 目标体积）

| 组合 | ASR | RaNER | 嵌入 | 合计 |
|---|---|---|---|---|
| 现状 | 588 fp32 | 388 fp32 | 98 int8 | ~1.0 GB |
| **全 int8（零重训）** | 154 | ~100 | 98 | **~360 MB** |
| ASR int8 + RaNER 换 MiniRBT-H288 int8 | 154 | ~13 | 98 | **~270 MB** |

**落地顺序**：① ASR 换官方 int8（下载即用）→ ② RaNER 现有权重 int8 导出（一次脚本）→ ③ 若还不够再走 MiniRBT/ERNIE-Medium 重微调。①+② 即可把 APK 从 1.0 GB 压到 ~360 MB，几乎不动精度。

## 14. 硬件选型与算力评估

### 14.1 负载画像（瓶颈分析前提）

| 组件 | 量化后体积 | 计算特征 | 约束类型 |
|---|---|---|---|
| ASR streaming-zipformer-zh int8 | 154 MB | **持续流式**，音频不停推理就不停 | **RTF（实时率）硬约束**——RTF<1 才不积压，目标 ≤0.5 |
| RaNER BERT-base int8 | ~100 MB | 突发（每次切句一次，seq≈64 token） | 单次几十~200ms，**非瓶颈** |
| embedding gte int8 | 98 MB | 突发 + 懒加载 | 非瓶颈 |
| GTCRN | 0.5 MB | 每 16ms 一 hop | 单核 ~3%，非瓶颈 |
| **常驻内存** | mmap 加载 | 模型文件可 mmap | **工作集峰值 ~600-800 MB**；4GB 设备勉强、6GB 舒适 |

**结论**：整个系统只有**一个硬约束——流式 ASR 的 RTF**。RaNER/嵌入都是"说完才算"的突发负载。
问题等价于：**什么级别的 ARM 核心能让 154MB 的 int8 流式 zipformer 跑到 RTF ≤ 0.5**。

### 14.2 实测锚点（公开数据）

| 数据点 | 说明 |
|---|---|
| RK3576（4×A72+4×A53）NPU 跑 streaming-zipformer-small 双语 | **RTF 0.304**（Rockchip 官方 rknn demo 实测）；纯 CPU 回退时 CPU 占 56%——A72 级核心跑 small 模型已接近极限 |
| Snapdragon 662（4×A73）跑 32M 级流式模型 | **RTF 0.30**（实测，单核，文件回放；实况麦克风 ≈0.35） |
| sherpa 官方速度测试 | SenseVoice int8：单核 A55 RTF ~0.7、单核 A76 快 ~4×——**A76 与 A55 之间差 3-4 倍**，核心代际是决定变量 |
| iPhone A15 跑同级流式 | RTF 0.08-0.10——旗舰大核绰绰有余 |

**外推**：zh-2025-06-30 是 large 架构（int8 154MB，约为 small 模型 5-6 倍计算量）。要让它的 RTF ≤ 0.5，
大致需要 **A76/A78 级大核 × 2 线程**的持续算力。

### 14.3 处理器分级表（对号入座）

| 档位 | 代表 SoC | CPU 核心 | zh-large int8 RTF 预估 | 判定 |
|---|---|---|---|---|
| **旗舰 2023+** | 骁龙 8 Gen2/Gen3、天玑 9200/9300 | 4×X3/X4 + 4×A715 | 0.1-0.2 | ✅ 从容 |
| **次旗舰** | 骁龙 7+ Gen2 / 778G、天玑 8000/8100 | 4×A78 @2.4G+ | 0.2-0.35 | ✅ **推荐档** |
| **中端** | 骁龙 695 / 6 Gen1、天玑 900/920 | 2×A78 + 6×A55 | 0.4-0.7 | ⚠️ 可用，2 线程 + 关 UI 动画；注意无风扇工业平板的**热节流** |
| **中端偏下** | 骁龙 685/662、Helio G85/G99 | A73/A75（**无 SDOT 指令**） | 0.8-1.5 | ❌ large 模型悬；**必须换 zh-small / zipformer-ctc-small**（83MB fp32 那批） |
| **工控板** | RK3588（4×A76+4×A55+6TOPS NPU） | A76 + **RKNN EP** | CPU ~0.5 / NPU 更低 | ✅ **工业场景首选**——sherpa-onnx 官方支持 rknn provider |
| 工控板下位 | RK3576 / RK3568 | A72/A55 | CPU >1 | ⚠️ 只能跑 small 模型，或赌 RKNN（见 14.4 风险） |
| 32 位老平板 | armeabi-v7a（A7/A53） | — | — | ❌ 直接排除（模型+运行时都装不下） |

**两个硬件层面的硬性要求**：
1. **ARMv8.2-A 的 SDOT/UDOT 点积指令**（A76 及以上才有）——int8 加速的关键；A72/A73 走通用内核，int8 也要慢 2-3 倍
2. **RAM ≥ 4GB（最低）**，6GB 舒适；8GB 才谈多路并发

### 14.4 反直觉风险：最新旗舰反而翻车

sherpa-onnx 官方 Android 包捆绑 **ONNX Runtime 1.27.0**，在**最新骁龙 8 Elite Gen 5（SM8850，Oryon 核）上
zipformer encoder 会静默算错**（输出全空、无报错），ORT 1.28.0 才修复（sherpa-onnx issue #3845）。启示：

- **选型别迷信最新旗舰**——中端 A78 芯片反而是"经过验证"的安全区
- 本方案 Native Service 编译时**钉死 ORT ≥ 1.28.0**（对应 §7.1 工具链要求）
- §8 验收新增一条"首次启动数值自检"（跑官方 test_wavs 对比输出，防静默算错）

### 14.5 选型建议（工业巡检场景）

**最低可行线**：4×Cortex-A76/A78 @ ≥2.0GHz + 6GB RAM + arm64-v8a + Android 10+。
典型落地：骁龙 695/天玑 8100 级别的工业平板，或 **RK3588 工控板（走 RKNN NPU）**。

**若客户预算只给到 A73 级（骁龙 662/4GB）**：不硬扛 large 模型，退到 `streaming-zipformer-zh-14M` 或
`zipformer-ctc-small-zh-2025-07-16`（小模型 + 热词加权补偿精度）——与巧妙设计 §5 的选型逻辑同源。

**验证方法**（不用买一堆平板）：sherpa-onnx 官方每档都有现成 APK（`apk-cn.html` 的 streaming asr 系列），
装到目标平板跑 `test_wavs` 计 RTF 即可——**先测 RTF 再定采购**，比看 SoC 规格书靠谱。
